# GeoQoE Pulse — Dynamic Mobile QoE & Demand Pressure Intelligence System

> **Read this before using any exported file.** This project has two
> honesty-critical distinctions. Both are explained in full immediately
> below — skip straight there if you're deciding what to train on or what
> to tell a judge.

GeoQoE Pulse is an explainable spatial-temporal decision-support prototype
for mobile network operators and regulators, built for a GeoAI hackathon. It
integrates real geospatial data — OpenCellID, Google Open Buildings V3,
OpenStreetMap, WorldPop, OpenDOSM, Ookla Open Data, and public transport
ridership — to estimate local demand pressure and, where real QoE
measurements exist, to relate that pressure to service quality.

The pipeline uses real GeoPandas geometry throughout: a study-boundary
polygon drives H3 grid generation via `h3.polygon_to_cells`, CRS-correct
area and distance calculations are performed in the Peninsular Malaysia RSO
projected coordinate system (`EPSG:3375`), and all spatial joins use proper
GeoPandas operations (`sjoin`, `sjoin_nearest`, `overlay`, zonal statistics)
rather than per-row approximations. Hotspot detection uses real `esda`
implementations (Getis-Ord $G_i^*$ and Local Moran's $I$, both with genuine
permutation-based p-values). Temporal features are leakage-free — warm-up
rows carry an honest `NaN` plus a `*_valid` flag instead of back-filled
values. The pipeline is deterministic: a single global seed, set once
before any randomness, is recorded in every `metadata.json`.

See **`CHANGELOG.md`** for the full list of fixes applied to reach this
version, each traced to the specific review finding it addresses.

## ⚠️ What's real, what's simulated — read this first

| | Real? | Use for |
|---|---|---|
| **Static GIS layer** — towers (deduplicated), buildings, OSM POIs/roads/transit, WorldPop population | ✅ Real, and — as of v3.1.0 — correctly scoped. Every `*_is_synthetic` flag for these sources is `False` across all 4,659 cells, and joins use real `sjoin`/`sjoin_nearest`/`overlay`/zonal-statistics. **v3.0.0 caveat, now fixed:** raw-file extraction previously used a hardcoded box far smaller than the real study boundary, so most cells outside that box got real-looking `count = 0` values that actually meant "outside the extraction window." Extraction now derives its bounds from the real grid (`extraction_bounds()`) — see `CHANGELOG.md`'s v3.1.0 section. **Any `data/outputs/` generated before this fix is stale and should be regenerated.** | Any modelling or dashboard use, once regenerated. |
| **`cell_static_qoe_baseline.parquet`** | ✅ Real. `ookla_dl_mbps`/`ookla_rtt_ms`/`ookla_tests` are the REAL Ookla quarterly averages for the 2,692 cells (57.78%) with tile coverage; `NaN` (not imputed) for the rest — flagged via `has_real_ookla_label`, not a column called `qoe_baseline_is_real`. Every feature is from the static layer above — zero QoE-derived circularity. | **The recommended dataset for any modelling claim you want to defend.** Train/validate on the 2,692 labelled cells; predict on the remaining 1,967. |
| **`cell_time_dataset.parquet`** (hourly panel, 782,712 rows = 4,659 cells × 168 hours) | ❌ **Simulated.** No organiser QoE dataset and no per-hour QoE source of any kind exists for this project. Ookla is a single *static, quarterly* average per cell — not hourly. Every `dl_median`/`ul_median`/`rtt_median`/`jitter_median`/`loss_median` value for every hour is generated by a diurnal-demand formula. Where a real Ookla anchor exists (`qoe_level_is_ookla_anchored == True`, 57.78% of cell-hours), the formula's *level* is re-centred on that one real number — the hourly *shape* is simulated either way (`qoe_hourly_shape_is_simulated` is always `True`). | Pipeline integration testing, dashboard demos, and building/testing a forecasting *framework* — **not** for reporting model accuracy as evidence of real predictive skill on real network behaviour. |

If your team needs to defend a technical claim to judges, lead with
`cell_static_qoe_baseline.parquet`. If you want to demo "here's what the
dashboard would look like with real hourly data,"
`cell_time_dataset.parquet` is exactly that demo — labelled as one, not
presented as measured.

**QoE index — what it actually is:** `target_qoe_index` is a **custom**
0–100 composite (logarithmic download/upload utility minus exponential
latency/loss penalty). It is *not* an ITU-T G.107, P.1203, or P.1204
implementation, and degradation is *not* a "QoE index < 70" rule — see
"QoE Target Design" below for the real rule.

**Study area note:** the boundary covers the Klang Valley *core* districts
(Putrajaya, Gombak, Hulu Langat, Klang, Kuala Langat, Petaling, Sepang) —
**Kuala Lumpur is not included** (no KL boundary file was available). See
`config.py`'s `STUDY_BOUNDARY_PATH` comment for exactly what's needed to add
it.

## 🔧 Pipeline Stages

`run_pipeline.py` runs ten stages in sequence:

| Stage | Description |
| :---: | :--- |
| **1** | **H3 Study Grid** — Loads the (correctly-scoped) study boundary and generates 4,659 H3 res-8 cells via `h3.polygon_to_cells`. Exports grid geometry to `data/processed/`. |
| **2** | **Spatial Joins & Baselines** — Real joins for all 7 raw sources (`sjoin`, `sjoin_nearest`, `overlay`, zonal stats), with OpenCellID records deduplicated to approximate physical sites. Computes the honest static Ookla baseline (2,692 cells with real measurements; the remaining 1,967 retain `NaN`, never fabricated). Assembles the simulated hourly panel, explicitly labelled. |
| **3** | **Temporal Features** — Leakage-free lag/rolling stats (`shift()` only, no backfill), with `*_valid` flags. |
| **4** | **Demand Pressure Index** — Real static-feature base (`demand_pressure_base`), plus a historical-QoE component explicitly flagged as circular with the simulated panel (`config.HIGH_LEAKAGE_RISK_FEATURES`). |
| **5** | **Spatial Features** — Real `libpysal` 1-ring adjacency; spatial lags, variance, rolling mean. |
| **6** | **Hotspot Detection** — Real `esda.G_Local` / `esda.Moran_Local`, 99 permutations, genuine p-values (verified: p-values bottom out at exactly 0.01 = 1/(99+1)), 90/95/99% confidence-band classifications, HH/LH/LL/HL quadrant labels. |
| **7** | **QoE Targets & Forecasting** — Computes the **custom** composite QoE index (0–100, log-utility download/upload minus exponential latency/loss penalty — *not* an ITU-T G.107/P.1203/P.1204 implementation), a 1–5 linear rescaling (`target_service_quality_1to5`), a binary same-hour degradation flag, and a 3-class severity label. **Degradation is threshold-based on raw dl/rtt, not a QoE-index cutoff**: `target_degradation_class` = 1 ("degraded") if `dl < 10 Mbps` or `rtt > 100 ms`; = 2 ("severe") if `dl < 5 Mbps` or `rtt > 150 ms`; `target_is_degraded = (target_degradation_class >= 1)`, so the two can never disagree. Also derives **next-hour forecast targets** (`target_is_degraded_next_1h`, `target_degradation_class_next_1h`, `target_qoe_index_next_1h`, `target_next_1h_valid`). |
| **8** | **Validation** — Structural checks (duplicate keys, invalid geometry, CRS consistency) plus regression guards: `target_is_degraded` vs. `target_degradation_class` consistency (hard error if they ever disagree — both are now derived from one threshold source, so this should never fire), and a check that `target_qoe_index`'s observed maximum can approach 100 (catches a silent weight-sum regression). |
| **9** | **Feature Dictionary** — `feature_dictionary.xlsx`: all 174 columns across the 4 output tables, `is_feature_for_current_target` / `is_feature_for_next_hour_target` flags, non-null percentages, dtypes, and `leakage_risk_note`. |
| **10** | **Export** — Compressed ZSTD `.parquet` files, `feature_dictionary.xlsx`, and `metadata.json` (including an explicit `simulation_disclosure` block and a `known_limitations` list) to `data/outputs/`. |

## 📐 Output Datasets & Deliverables

1. **`cell_static_features.parquet`** (4,659 cells × 29 columns) — real static GIS features only (towers, buildings, POIs, roads, population). No QoE columns at all.
2. **`cell_static_qoe_baseline.parquet`** (4,659 cells × 34 columns) — `cell_static_features` plus real Ookla-anchored QoE labels. 2,692 cells (57.78%) have a real `ookla_dl_mbps`/`ookla_rtt_ms`/`ookla_tests`; the remaining 1,967 are `NaN`, flagged via `has_real_ookla_label` (not a column called `qoe_baseline_is_real`).
3. **`cell_time_dataset.parquet`** (782,712 rows × 99 columns = 4,659 cells × 168 hours) — the simulated hourly panel: temporal lags, rolling stats, spatial lags/variance, Gi*/Local Moran's, demand pressure index, historical hotspot frequency, plus same-hour and next-hour targets folded in.
4. **`qoe_targets.parquet`** (782,712 rows × 12 columns) — a dedicated target-only table mirroring the target columns in `cell_time_dataset.parquet`, for a lighter join when only labels are needed.
5. **`feature_dictionary.xlsx`** (174 rows × 8 columns) — `file`, `column`, `dtype`, `pct_non_null`, `is_feature_for_current_target`, `is_feature_for_next_hour_target`, `leakage_risk_note`, `description`.
6. **`metadata.json`** — pipeline version (`3.0.0`), timestamp, CRS, seed (`42`), git commit, raw-file checksums, `synthetic_fallback_summary`, `simulation_disclosure`, `high_leakage_risk_features`, and `known_limitations`.

## 🛠 Model Training Instructions

### Option A (recommended): the honest static baseline

```python
import pandas as pd

df = pd.read_parquet("data/outputs/cell_static_qoe_baseline.parquet")
labelled = df[df["has_real_ookla_label"]]          # 2,692 cells — real Ookla targets
unlabelled = df[~df["has_real_ookla_label"]]        # 1,967 cells — real features, prediction targets

feature_cols = [c for c in df.columns
                if c not in {"h3_index", "ookla_dl_mbps", "ookla_rtt_ms", "ookla_tests",
                              "has_real_ookla_label", "qoe_risk_label"}]

X, y = labelled[feature_cols], labelled["ookla_dl_mbps"]  # or classify qoe_risk_label
# Train/validate on `labelled` (spatial k-fold — there's no time dimension
# to split on here), then predict on `unlabelled`.
```

Every number in `X` and `y` here is real. This is the dataset to point a
hackathon judge at if asked "is this real data."

### Option B: the simulated hourly panel (pipeline/dashboard demo only)

Query the feature dictionary directly rather than hand-maintaining an
exclusion list — this also self-documents which mode you're in:

```python
import pandas as pd
from xgboost import XGBClassifier

df_panel = pd.read_parquet("data/outputs/cell_time_dataset.parquet")
df_targets = pd.read_parquet("data/outputs/qoe_targets.parquet")
df_dict = pd.read_excel("data/outputs/feature_dictionary.xlsx")

# Next-hour forecast target — the recommended primary target, and the ONLY
# mode where current-hour QoE values (dl_median, rtt_median, their
# derivatives, and same-hour spatial lags) are legitimate features, because
# they're genuinely observed before the hour being predicted.
next_hour_features = df_dict[
    (df_dict["file"] == "cell_time_dataset") &
    (df_dict["is_feature_for_next_hour_target"] == True)
]["column"].tolist()

df_panel = df_panel.sort_values(["h3_index", "timestamp"]).reset_index(drop=True)
valid = df_targets["target_next_1h_valid"] == 1     # drop end-of-series warm-up rows
X = df_panel.loc[valid, next_hour_features]
y = df_targets.loc[valid, "target_is_degraded_next_1h"]

split_point = int(len(X) * 0.80)                    # temporal holdout
X_train, y_train = X.iloc[:split_point], y.iloc[:split_point]
X_test, y_test = X.iloc[split_point:], y.iloc[split_point:]

model = XGBClassifier(n_estimators=100, max_depth=6, random_state=42)
model.fit(X_train, y_train)
print("Test Accuracy:", model.score(X_test, y_test))
print("LABEL CLEARLY: synthetic-panel pipeline validation only — "
      "not evidence of real-world predictive performance.")
```

If you need the same-hour target (`target_is_degraded`) instead, filter
`df_dict["is_feature_for_current_target"] == True` — it additionally
excludes every raw QoE column (`dl_median`, `dl_mean/std/p95`, `ul_*`,
`rtt_*`, `jitter_median`, `loss_median`) and their same-hour spatial lags
(`spatial_lag_dl_median`, `spatial_lag_rtt_median`), which would otherwise
leak the answer.

## QoE Target Design (corrected — read if anything else you have says otherwise)

`target_qoe_index` (0–100) and `target_service_quality_1to5` (1–5) are a
**custom composite index** — logarithmic download/upload utility minus an
exponential latency/loss penalty, with weights that sum to 1.0 so the index
can genuinely reach 100. They are **not** an ITU-T G.107 E-model MOS and
**not** a P.1203/P.1204 implementation; no such standard is implemented
anywhere in this codebase.

Degradation labels are **not** derived from a QoE-index cutoff. They come
from `config.QOE_THRESHOLDS`, applied directly to `dl_median`/`rtt_median`:

- `target_degradation_class = 1` ("degraded") if `dl < 10 Mbps` **or** `rtt > 100 ms`
- `target_degradation_class = 2` ("severe") if `dl < 5 Mbps` **or** `rtt > 150 ms`
- `target_is_degraded = (target_degradation_class >= 1)`

Both labels are derived from the same threshold source in one function
call, so they cannot disagree with each other — this is enforced by
construction, not just checked at validation time.

## 🔑 Key Design Decisions

- **CRS discipline** — WGS84 (`EPSG:4326`) for storage/export; all distance/area/length calculations happen after reprojection to Peninsular Malaysia RSO (`EPSG:3375`). Raw degree-based area/distance math is never used.
- **Synthetic transparency, split into two honest signals for QoE** — every real-vs-synthetic static feature is flagged via `<feature>_is_synthetic`. For the hourly QoE panel specifically, `qoe_level_is_ookla_anchored` (was a real anchor used to re-centre the formula?) and `qoe_hourly_shape_is_simulated` (always `True`) replace a single ambiguous flag that would otherwise imply measured data exists where it doesn't.
- **Temporal integrity** — `shift()`-only, `*_valid` flags, no backfill. Warm-up null counts are exact multiples of the cell count (4,659 / 9,318 / 111,816 for 1h/2h/24h lags), confirming genuinely causal construction.
- **Target integrity** — same-hour and next-hour degradation labels share one threshold source and cannot disagree; a genuine 1-hour-ahead forecast target exists alongside the same-hour classification target.
- **Leakage discipline, target-mode-aware** — `feature_dictionary.xlsx`'s `is_feature_for_current_target` / `is_feature_for_next_hour_target` columns replace a single static exclusion list, because what counts as leakage depends on whether you're predicting the current hour or the next one.
- **Reproducibility** — a single global seed (`config.GLOBAL_RANDOM_SEED = 42`), set once before any randomness. Every run's `metadata.json` records the seed, git commit, and raw-file checksums.
- **Honesty about what's real** — `cell_static_qoe_baseline.parquet` exists specifically so the project has a modelling-ready deliverable that requires zero caveats. `cell_time_dataset.parquet` remains useful, clearly labelled as what it is.

## Known limitations (also in every `metadata.json`)

1. No real per-hour QoE measurement source exists — `cell_time_dataset.parquet` is a labelled simulation.
2. No real network capacity/traffic/utilisation data exists — demand-pressure features are activity proxies, not a capacity measurement. Say "QoE degradation associated with estimated demand pressure," not "confirmed congestion."
3. Kuala Lumpur is not covered by any layer in this project — no KL boundary file was available.
4. `tower_count` is a deduplicated approximation of physical sites, not an authoritative operator inventory.
5. `target_qoe_index` / `target_service_quality_1to5` are a custom composite index, not a validated ITU-T G.107 MOS, and are not related to ITU-T P.1203/P.1204.
6. `demand_pressure_index` (and its pre-spatial version) is circular with the simulated QoE panel via its historical-QoE component — use `demand_pressure_base` instead for a non-circular, real-data-only feature.
